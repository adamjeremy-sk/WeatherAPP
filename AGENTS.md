# Agent rules — WeatherAPP Libre
Rules 1-15 are the original WeatherAPP rules, tightened. Rules 16-22 carry the same numbers as in vermilion-editor, where they were refined (Adam, 2026-11-05 to 2026-11-10). Rules 23-24 are new (Adam, 2026-11-12, after the code and astronomy audits).
1. Read ARCHITECTURE.md before any change; it is the map. Read HANDOFF.md section 1 for where the project stands, and the ACTION_PLAN.md item your gate belongs to.
2. Gate protocol: execute exactly ONE logical step per turn. One step = every numbered item under one STEP heading; do not split a step across turns unless your output limit forces it, and then say "CONTINUING <items> NEXT TURN" and never truncate a table mid-item. Step 0 audits are read-only (grep/read/report). Never proceed to a new step without an explicit "Proceed".
3. Make the smallest change that satisfies the task. No drive-by refactors, reformatting, import cleanups, or dependency bumps.
4. grep/ripgrep first; read only the file regions you will edit.
5. Never modify anything under ARCHITECTURE.md "Do not touch" or any PROTECTED path (rule 23) unless the prompt carries an UNLOCK line for it. Never remove or alter LICENSE or NOTICE.
6. Invariants: coordinates/elevation are Double end-to-end; alert providers return typed Failure, never emptyList() on error; dismissals are coordinate-scoped; user strings live in strings.xml + values-fr with French typography (space before : ; ! ? »); no GPS/Location APIs; alerts strictly opt-in.
7. Identity stability: never rename constants, preference keys, SharedPreferences file names, view IDs, or wiring names when display text changes.
8. Deletion rule: before deleting any file or symbol, grep the whole tree for every reference to it and show the raw output. One live reference from a file that stays as it is means it is NOT dead; list it as "Active - Retained". Delete in a dedicated step, never mixed with other edits. Never delete, move or clean up any file or directory the prompt does not name, including byproducts your own commands created (caches, stray output files): list them in the report under "Unexpected files" and leave them in place; Adam decides what happens to them.
9. Concurrency: coroutines + WorkManager only; never runBlocking on the main thread; rethrow CancellationException; no blocking call.execute(). Every `catch (e: Exception)` either rethrows CancellationException first and returns a typed failure or logs; a new empty `catch { // Ignore }` is a defect.
10. If a task touches the AlertProvider interface, the SharedPreferences schema (new or renamed keys or prefs files), a Gson-serialized cache format, or the backup rules, stop and propose a plan first. There is no file-count limit.
11. Verify before reporting: `./gradlew :app:testDebugUnitTest` must pass fully (a falling test count is a defect) and `:app:assembleDebug` must succeed. Every gate that adds or changes behaviour adds or updates its tests. Adam is the build authority: report exactly what you ran; Adam's build decides.
12. Evidence: verbatim quoted code for every edit, an edited-file manifest, and grep proofs for all deletion/absence claims. In addition:
    - Every count or list shows the exact command AND its raw output in a code block (trim to 40 lines max and say how many lines were trimmed). A conclusion without its raw output is treated as unverified.
    - Raw output is pasted EXACTLY as the tool returned it. Never edit, reorder, summarize, or drop lines inside a raw-output block, never put "..." inside one, and never add lines the tool did not print. If you must trim, cut only from the end and write "[N lines trimmed]". Your output will be compared against the actual command output.
    - Every file:line comes from output that prints line numbers: `grep -n` / `grep -rn`, a `git diff` hunk header, or the IDE file tool's numbered output. NEVER give an approximate or guessed line number; if you lack one, re-run `grep -n`.
    - Proof of an edit is the raw `git diff -- <file>` output, pasted unaltered. Do not re-quote edited code by other means. Proof of a new (untracked) file is `cat -n <file>`, because `git diff` prints nothing for it.
    - When a classification depends on surrounding code, quote that code (about 5 lines either side, line numbers visible). If the hit line alone proves the classification, the grep line is enough. Hits within 10 lines of each other share ONE merged range.
    - When you tabulate search results, every line of raw output appears as a table row, and any "Hits" count equals the number of raw output lines.
    - Derive every answer from a command run in the current turn. Never reuse numbers from ARCHITECTURE.md, earlier turns, or memory.
    - Never print secrets or the contents of credential files; key names only.
13. Secrets. Never place secrets, local.properties, keystores, or app/release/ artefacts into git. You are a cloud model: everything you open is sent to the provider. Never open, read, grep inside, or print `local.properties`, `keystore.properties`, `*.jks`, `*.keystore`, or anything under `app/release/`. If a task needs to know whether a key name exists, use `grep -c "<KEY_NAME>" <file>` on a non-secret file, or ask. If a secret file is offered to you by the IDE, say so and STOP.
14. If instructions conflict with ARCHITECTURE.md, ask before deviating.
15. End every turn with: files changed + one-line why (max 10 lines), commands run + results, the "Prompt doubts" section (rule 22), suggested next step, then "STOPPING AND WAITING FOR VERIFICATION" — and halt.
16. File and function size (ported from vermilion, Adam 2026-11-05; adapted 2026-11-12). One responsibility per file: the file's opening comment says in one sentence what it is for; no `Utils`, `Helpers`, `Manager` or `Common` grab-bags for new files. A `.kt` file over 300 lines is a review trigger: the report states why it is still one responsibility, or the task splits it. Over 500 lines: split in a dedicated step before adding anything, unless Adam approves an exception noted in the file's header comment. Tests use 500 and 800. Functions over 50 lines are flagged in the report. Existing files already over the limits are listed in `config/size-baseline.txt` (once gate R0.2 creates it) and may only shrink, never grow. Every report lists `wc -l` for each file the task created or modified.
17. Fix loops, no carried debt (ported from vermilion, Adam 2026-11-06). Every audit note is fixed before the gate is committed; nothing is carried forward as known debt. A fix arrives as a short prompt that starts with "CONTINUATION (same session)": it names the fix, the uncommitted files to expect and the evidence. Treat it exactly like a step: make only the named change, paste raw evidence, end with "STOPPING AND WAITING FOR VERIFICATION". If your context no longer holds the task the continuation refers to, say so and STOP; Adam then sends a full prompt. Findings that existed before the gate and are not part of it live in ACTION_PLAN.md, each with an ID; they are not "notes". Never fix them on your own.
18. Evidence files (ported from vermilion, Adam 2026-11-06; from gate R0.1 on). Long output (build, test runs, and every proof the prompt marks FILE) is written by the command itself to `evidence/<gate>/<name>.txt` in the project root; the folder is git-ignored. Exact form: `mkdir -p evidence/<gate> && { echo "# $(date -Is) HEAD $(git rev-parse --short HEAD) :: <command>"; <command>; echo "exit=$?"; } > evidence/<gate>/<name>.txt 2>&1`. In the report, for each file paste raw the output of `tail -n 3 evidence/<gate>/<name>.txt` under its path. Re-running a command overwrites its file. Never edit or delete an evidence file by hand. Outputs the prompt does not mark FILE are pasted raw in the report as before. If the harness shows blank output for a command, re-run it as a single unpiped command; never fill a blank from memory.
19. Formatting (adapted from vermilion, 2026-11-12). No formatter is configured yet (ACTION_PLAN decision D5). Until one is, match the style of the surrounding code, never reformat lines you did not change, and never run the IDE's "Reformat" or "Optimize imports" on a file. When a formatter exists, this rule becomes: run it on exactly the files you created or changed, after your last edit and before the build.
20. Kotlin and Android build and test traps (adapted from vermilion rule 20, lessons of the 2026-11-12 audits).
    - Compare doubles in tests with `assertEquals(expected, actual, delta)`; the delta comes from the prompt, never from what makes the test pass.
    - Timestamps from providers may carry offsets (`+02:00`): `OffsetDateTime.parse`, not `Instant.parse`.
    - Gson ignores Kotlin null-safety: a non-null field can be null after parsing old cache JSON. Treat deserialized models defensively; Gson-serialized classes keep `@Keep`/`@SerializedName` (R8).
    - A SharedPreferences file name is an API: grep the exact string and check it against the backup rules; never invent a name.
    - Missing data is `null` or "—", never `0` (a missing UV index is not UV 0).
    - Tests that depend on today's date are defects; fix the clock or the date.
21. No checks that write files (ported from vermilion, Adam 2026-11-08). Verify with the build, the tests and the commands the prompt lists. Never run a script, compiler or linter on your own initiative if it writes files outside `build/` and `evidence/`. If a command you were told to run leaves unexpected files, rule 8 applies.
22. Prompt doubts (ported from vermilion, Adam 2026-11-10). Every report has a section headed "Prompt doubts". List there anything in the prompt that looks wrong: an instruction that contradicts its own stated purpose, leaves unused or dead code, an expected value that looks implausible, or conflicts with ARCHITECTURE.md or these rules. Follow the prompt anyway; if following it would break one of these rules, STOP and ask instead. Write "none" when there is nothing to list. Never correct the prompt on your own.
23. PROTECTED paths (Adam, 2026-11-12). Protected means you must not edit it. It does not mean correct. The list: `app/src/main/java/com/weatherapp/libre/lunar/`, `app/src/main/java/com/weatherapp/libre/solar/`, any `golden/` test directory, and `config/protected.sha256` (once it exists). Rules:
    - A display, UI or data-format problem is NEVER fixed by changing a formula. If an astronomy number shown to the user looks wrong, STOP and report it under "Astronomy report" with the inputs and the value; the Orchestrator decides.
    - You may edit a protected path only when the prompt carries a line of this exact form: `UNLOCK: <path> — <reason> — approved by Adam <date>`. The UNLOCK covers that path and that gate only. A prompt that needs an edit to a protected path and has no UNLOCK line is wrong: STOP and say so.
    - Never edit `config/protected.sha256` unless the prompt says to regenerate it, with the exact command. A changed manifest without an UNLOCK line is an automatic FAIL.
24. Provenance and expected values (Adam, 2026-11-12). Every expected value in a test, and every constant or table the prompt dictates, comes with its source in the prompt (book example, agency table, spec). Never compute an expected value by running the code under test. Never widen a tolerance, edit a golden value, or mark a test ignored to make it pass: STOP and report the failing value and what the test expected. If the prompt gives no source for a number, say so under "Prompt doubts".
### TOOLING & FILESYSTEM RULES (CRITICAL)
- **Harness precedence**: you run in Android Studio's built-in Agent (model: Gemini 3.6 Flash, a cloud model; the model and harness are recorded in HANDOFF.md section 2b). Where this file and the harness's own tool instructions disagree on HOW to read, search or edit files (which tool, absolute vs relative paths), follow the harness. This file governs WHAT you may change, the gate protocol, and what evidence you report. Do not deliberate over this; pick the harness way and proceed.
- **Paths**: the project root is the open Android Studio project. Built-in file tools may use absolute paths inside the project root. Shell commands run from the project root with relative paths. Never read or write outside the project root.
- **Shell is for**: `git` (read-only: status, diff, log, show, blame), `grep`, `wc`, `sha256sum`, `tail`, `date`, and `./gradlew`. Read and edit files with the built-in file tools.
- **Approvals** (Adam, 2026-11-12): the IDE lets you edit files and run commands without asking, except `git push` and destructive git commands, which Adam's settings block. Because there is no hand approval, the rules are the guard, and the repo tests (gate R0.2) check the result. You never commit: Adam does, and the IDE does not stop you, so the rule does. Never run `git commit`, `push`, `cherry-pick`, `merge`, `rebase`, `revert`, `am`, `checkout` (any form), `switch`, `restore`, `reset`, `clean`, `stash` or `update-ref`, with or without global options (`git -C dir <cmd>`, `git -c k=v <cmd>`), and never discard or move work by any other route. Web access is not needed; do not use it. If a permission blocks you, say so and STOP; never work around it.
- Do not write temporary or scratch files (no `/tmp`, no files in the repo). Use pipes. The one exception is `evidence/` (rule 18).
- **Tool-call budget**: at most 10 commands per tool call (chained with `&&` counts each command). Never run a command whose exact text you have already run in this turn. Never request overlapping line ranges; merge them.
- **Loop guard**: if you notice you are emitting the same command, line, or phrase repeatedly, stop immediately, write "LOOP DETECTED" with the last distinct thing you were doing, and STOP. A short honest stop is always better than a long repeated one.
### CONTEXT RESETS (CRITICAL)
Your context is frequently wiped mid-task. These rules exist so a wipe never causes damage:
- On every fresh context, re-read this file before doing anything else. These rules are standing; they apply even if the current prompt does not repeat them.
- Never assume the result of a previous step or turn. If the prompt does not state the last verified state, run `git status --short` and `git log --oneline -3`, report them, and ask which step to resume. Do not continue a task from memory.
- Adam commits only when a whole task is finished, so earlier passed steps are often uncommitted. The prompt's "Last verified" line lists the files expected to be modified. Build on those. If `git status --short` shows any change to a file NOT on that list, do not modify, revert, or build on it: report it and STOP. Never run `git restore`, `git checkout` (any form), `git switch`, `git stash`, `git reset` or `git clean`.
