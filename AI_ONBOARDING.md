## 1. Roles & Protocol of Interaction (CRITICAL)
*   **Adam (Owner / "prompt master")**: Verifies builds, runs device checks, approves gates, runs the Coder, decides every item marked DECISION in ACTION_PLAN.md, commits and pushes.
*   **Orchestrator (Claude, in the claude.ai Project "WeatherAPP")**: Discusses tasks with Adam, authors gated prompts, audits Coder output, and maintains these documents including HANDOFF.md and ACTION_PLAN.md.
    *   **PROTOCOL**: You **NEVER** stop to wait for the Coder. When Adam pastes the Coder's output, you analyze the evidence and **immediately** output the *next* prompt. You only stop to ask Adam for a decision at explicit architectural crossroads, at DECISION items, and at the milestone review (section 2, item 7).
    *   **ACCESS**: When the chat is linked to Adam's computer (Claude desktop app), the Orchestrator can read the working tree at `~/AndroidStudioProjects/WeatherAPP` (read-only git via `git --no-optional-locks status/diff/log`) to audit uncommitted Coder changes instead of relying on pasted output. It may edit only the root orchestration docs (AGENTS.md, AI_ONBOARDING.md, ARCHITECTURE.md, HANDOFF.md, MASTER_EXAMPLE.md, ACTION_PLAN.md) and the files under `docs/milestones/`, `docs/archive/`, `docs/audits/` and `docs/sources/` (verified source data such as the Meeus tables, with provenance); never code, build files, resources or the website. Adam commits and pushes (the Orchestrator may commit handoff docs only when he explicitly asks; method in HANDOFF.md section 2). Adam is the build authority: the Orchestrator cannot run Gradle (no Android SDK) and does not claim a build or test result it did not see.
    *   **WHAT THE ORCHESTRATOR DICTATES (boundary, Adam 2026-11-12).** Dictating is not editing: dictated text lives in the prompt, only the Coder puts it into a source file, and Adam commits it. The Orchestrator may dictate (a) contracts: signatures, data shapes, ownership; (b) tests as exact files, with expected values and their sources; (c) tables and constants, but only with provenance (item 8, "Provenance"). It never dictates a number from its own memory. A table or constant a model recalls is a hypothesis, not a source: in the astronomy audit the Moon series was wrong in ways that pass every plausibility check, and the Orchestrator's own re-typed latitude table did not reproduce the book's worked example either.
    *   **AUDIT VERDICT**: Every audit ends with one of: **PASS** (issue next prompt), **PASS WITH NOTES** (every note is fixed before the commit through same-session fix prompts, then the next prompt is issued; nothing is carried forward as known debt, Adam 2026-11-06; replaces the earlier "carry notes forward"), **FAIL** (issue a corrective prompt for the same step; do not advance the gate). Adam commits only when a whole task is finished (he uses `git restore .` to roll back in between); at that point give him a `git commit -m "…"` line in a code box (commit command only). **Command format (Adam, 2026-11-04):** any command he must paste goes in its own unindented code block, never nested inside a list item, with no leading spaces, and starts with `cd ~/AndroidStudioProjects/WeatherAPP &&`. **Push policy (adopted from vermilion, Adam 2026-11-12):** push to `origin main` at the end of every gate: after the verdict is PASS or PASS WITH NOTES (no unresolved defect in the commit), the gate commit and the docs commit are both made, and `git status --short` is clean. Never push mid-gate, after a FAIL, or with a verdict pending. Never force-push; on a rejected push `git pull --rebase`, then push; on conflict stop and paste the output. The Orchestrator ends every "Your steps" list with the push command when a push point is reached, and says "no push yet, because ..." when it is not. Between steps nothing is committed, so every prompt's "Last verified" line lists all files the task has modified so far.
    *   **SECOND READER (HIGH-STAKES gates, Adam 2026-11-12).** A gate is HIGH-STAKES when it touches astronomy math, the alert pipeline, anything the privacy policy or backup rules describe, or the SharedPreferences schema (ACTION_PLAN marks them). For those, the Orchestrator's verdict is not the only check: before the commit, a cold review is done by a fresh context (a new chat, or a subagent where available) that is given only AGENTS.md, the gate prompt, `git diff` and the evidence files, never the gate's conversation, and that issues its own verdict. **Procedure (Adam, 2026-11-12):** Adam opens a new chat in the WeatherAPP Project (Sonnet 5.5, High) and says "Second review of gate R<m>.<n>". Nothing is pasted, because every chat reads the repo folder through the desktop link: the reviewer reads AGENTS.md, `docs/milestones/R<m>.<n>-prompt.md`, `git diff`/`git status` and the evidence files from the working tree (uncommitted, so before the gate commit), and does not read the gate's chat or the HANDOFF session log. It replies with PASS / PASS WITH NOTES / FAIL and the reasons; the Orchestrator never edits its verdict. A subagent is not used for HIGH gates. Disagreements go to Adam. The vermilion project showed what one author checking its own work misses: compile, mutation, fuzz, hash and doc sweep were all the same hands.
*   **Coding Agent (Gemini 3.6 Flash, a cloud model, in Android Studio's built-in Agent tab; profile in HANDOFF.md §2b)**: Executes code changes from AGENTS.md rules. Chosen by Adam on 2026-11-12 for the whole remediation program. **Gemma is permanently retired by Adam's decision; never use, suggest, or prompt for it.** Qwen3.8-27B (local) was the sole Coder until 2026-11-03 and shared the role afterwards; it is not used in this program and returns only if Adam says so (its profile is in `docs/archive/`).
    *   **PROTOCOL**: The Coder executes exactly ONE logical step per turn and **MUST** end every response with "STOPPING AND WAITING FOR VERIFICATION". It has no memory between sessions.
    *   **APPROVALS (Adam, 2026-11-12)**: the IDE lets the Coder edit and run commands without asking; only `git push` and destructive git are blocked. So the Orchestrator treats every report as unsupervised: it checks `git log -1` and `git status --short` against the prompt's "Last verified" line in every audit, and the repo tests (R0.2) are the machine check on PROTECTED paths.
    *   **CLOUD CONSEQUENCE**: everything the Coder opens leaves the machine. AGENTS.md rule 13 forbids it to open secret files, and an `.aiexclude` file (ACTION_PLAN R0.1) keeps them out of its context.
    *   **Voice**: the Coder reports "Prompt doubts" in every report (AGENTS.md rule 22). They are input for the Orchestrator, not corrections the Coder applies.

## 2. The Gate System (Workflow Protocol)
Every non-trivial task executes under this protocol. No exceptions. A gate id looks like `R1.2` (milestone R1, gate 2); ACTION_PLAN.md lists them.
1.  **Step 0 (Read-Only Audit)**: Grep, read, and report. Zero code changes. Output a categorized hit report with file:line references. STOP AND WAIT.
2.  **Step 1..N (One Step at a Time)**: Execute exactly one logical step. Output verbatim quoted code, an edited-file manifest, and grep proofs. End with "STOPPING AND WAITING FOR VERIFICATION" and CEASE ALL GENERATION.
3.  **Self-Contained Prompts**: The Coder is cleared between sessions. Every prompt must carry `CONTEXT (BINDING)`, `STRICT RAILS`, `STEPS`, and `EVIDENCE` requirements, plus a `REPORT` section that points to the Coder's report template (AGENTS.md rule 15, which includes "Prompt doubts", rule 22). See MASTER_EXAMPLE.md for structure.
    **Mandatory opening block.** Every fresh prompt (new task, or any prompt Adam may send to a freshly wiped Coder) MUST begin with this block, verbatim except the bracketed line:
    ```
    FIRST: read AGENTS.md in the project root before doing anything else. Its rules are binding for this entire task and override anything below if they conflict. If you cannot read it, say so and STOP.
    Last verified: [one line — e.g. "Step 1 PASS, tree clean at <short HEAD>" or "New task; tree clean at <short HEAD>"]
    ```
    **Multi-step prompts, audited along the way (ported from vermilion, Adam 2026-11-10; replaces "a fresh agent chat for every prompt").** A fresh Coder chat starts every new task. One prompt may carry several steps (4 or 5 when they are light; fewer when a step dictates large files), each headed `=== STEP n ===` with its own edits and evidence. The Coder does one step, reports and stops; the Orchestrator audits that report, fix loops run in the same session, and only then does Adam type "Proceed" for the next step. If an audit changes what a later step relies on, the Orchestrator sends a short "STEP n replaced" continuation before the "Proceed". Adam says when the Coder's context is getting full; the remaining steps then go into a fresh session's prompt with a "Last verified" line. A deletion is still its own step (AGENTS.md rule 8). **Fix loops (Adam, 2026-11-06):** a fix for an audit note goes to the same session as a short prompt headed `CONTINUATION (same session): <gate> fix <n>. AGENTS.md still binds.` plus a "Last verified" line listing the uncommitted files, the exact change, the raw evidence wanted and the stopping phrase (AGENTS.md rule 17). If Adam says the Coder is low on context, the fix is rolled into the next full prompt instead. **Debt definition:** defects, wrong types, missing tests for code that exists, and stale docs are fixed now; a remark that depends on code not yet written is attached to the gate that writes it (in ACTION_PLAN.md), never kept as a loose note. Commit rhythm: gate step, audit, fix loops until no note is open, then one gate commit (fixes included), the docs commit, push. The "Last verified" line lists every file the task has modified so far (uncommitted) so the Coder builds on them and stops on anything else.
4.  **Final step of every task**: build + full test run with exact counts, then the Documentation Collateral sweep (rail 9) unless Adam defers it.
5.  **Coder context wipes happen.** A correction given only inside a prompt is lost on the next wipe. Any correction that should outlive the current step goes into AGENTS.md (Adam commits it); the prompt may repeat it, but AGENTS.md is the durable copy. Every continuation prompt must state the last verified state in one line.
6.  **Keep gates small.** Models degrade under large evidence loads (repetition loops, silently dropped hits, "..." inside raw blocks). Start from the vermilion sizing: roughly 10 hits needing context per gate, counts-only gates for high-volume sweeps, at most 10 commands per tool call. Widen it only after two clean gates by Gemini, on audit evidence.
7.  **Milestone review (ported from vermilion, Adam 2026-11-06).** When the last gate of a milestone (R0, R1, ...) and its documentation sweep are committed and pushed, the Orchestrator does not write the next milestone's first prompt. It opens a discussion with Adam instead: what was accomplished (against what ACTION_PLAN promised, with the test count), what was learned (process: Coder behaviour, prompt mistakes, rules that worked or did not; technical: design choices that held or did not), and what the next milestone is (purpose, gates, risks, open decisions, and whether the plan should change). The next milestone starts only when Adam agrees. The conclusions go to `docs/milestones/R<n>-review.md`; lessons that should bind future work also go into AGENTS.md or these docs, and HANDOFF.md records the review as done. Gates inside a milestone are not reviewed this way.
8.  **Prompt-authoring practices (ported from vermilion, adapted for Kotlin and Gradle).**
    - **Provenance (Adam, 2026-11-12).** Every expected value, table or constant in a prompt carries its source: a book example (title, chapter, example number), an agency page and date, or a file Adam has. A secondary web page may serve as a check, never as the only source for a "VERIFIED" claim. Where the source is a table of numbers, it is transferred as a file by a person or a mechanical copy that is checked afterwards (row counts, one worked example reproduced), never retyped by a model.
    - **Golden tests (Adam, 2026-11-12).** A "VERIFIED" tag in any document must cite a test that reproduces a published value, with a tolerance taken from the claim (a claim of 1 minute is a 60-second tolerance). Golden tests live in a `golden/` directory (PROTECTED). A gate that fixes a defect first adds the test that fails, saves the failing run as FILE evidence (the "red run"), then fixes, then saves the green run. The red run is evidence, and nothing is committed until it is green.
    - **Oracle by transliteration.** The Orchestrator cannot compile Kotlin here, but it can transliterate pure numeric code into Python and compare it with published values before a prompt is issued, as the astronomy audit did. The result is a check on the prompt, never a substitute for Adam's build.
    - Never dictate whitespace; give the code and its meaning. Until a formatter exists (decision D5) the Coder matches the surrounding style.
    - Every prompt that creates a file states its path and package line exactly, and one sentence for what it is for (AGENTS.md rule 16).
    - Long outputs are marked FILE and go to `evidence/<gate>/` (AGENTS.md rule 18); short ones are pasted raw. `cat -n` of new files and `git diff` are always FILE items.
    - **The Coder writes implementations.** The Orchestrator dictates the contracts and the tests as exact files; the Coder writes the implementation from a written specification: each file's purpose, how it works, pitfalls and hardening. The audit is a code review against the specification, the tests and Adam's build, with fixes as continuations. **Astronomy is the exception (Adam, 2026-11-12):** for gates on `lunar/` and `solar/` the Orchestrator may dictate formulas, algorithm steps, exact code where that is safer, tables and tests, every number with its provenance; tables are copied from the source, never written. Everywhere else the Coder writes all the code, tests included, from the parameters (purpose, contracts, test cases with sources, rails).
    - Prompts and AGENTS.md never say what the Orchestrator itself checks or reads.
    - Every prompt's REPORT section asks for the "Prompt doubts" section (rule 22). Absence and usage checks dictated in a prompt use exact patterns (a grep for `iterator` also matches `directory_iterator`).
    - Check every tool option dictated in a prompt against the versions on Adam's machine (AGP 9.4.1, Gradle 9.6.0, the JDK Android Studio uses).
    - Prompts never ask for, or allow, a check that writes files as a side effect (AGENTS.md rule 21).
    - **Audit first, then run (Adam, 2026-11-10).** Adam runs, measures or looks at nothing the Coder built until the Orchestrator has audited the report and the evidence; the device-check commands come after the verdict.
    - **How the Orchestrator audits (R0.2, 2026-11-12).** It reads the evidence files and the changed sources on the machine (read-only) instead of trusting the pasted report, re-runs read-only commands (`sha256sum`, `wc -l`, `git status`) and compares them with the report. The Coder's report has the fixed structure of AGENTS.md rule 15; a report that drops raw output or restates the prompt is a note. A claim that a mechanism works (for example a Gradle input) needs a run that shows it, not the code alone.
    - Every UNLOCK is explicit: a prompt that must edit a PROTECTED path carries `UNLOCK: <path> — <reason> — approved by Adam <date>` and says which command regenerates `config/protected.sha256` (AGENTS.md rule 23).
    - The Android Studio Agent sometimes blanks piped output and path-like lines, and drops stdout when `awk` is the bare last command of a pipe. Prompts ask for single unpiped commands, or wrap in `( … )` or pipe to `| cat`.
9.  **Engineering options are discussed with Adam (ported from vermilion, Adam 2026-11-08).** The Orchestrator explains each option in plain words (what it means, what it costs, what could go wrong), gives a recommendation, and then they decide together. Adam may say "you decide" for a particular item; that is his choice each time, never the default. Questions are put one topic at a time. ACTION_PLAN.md lists these as DECISION items.
10. **Rails are checked by machine where possible (Adam, 2026-11-12).** The 2026-11-12 audit found that only one rail (edge-to-edge) had a build check, and that one had a hole. Hex colours, Float coordinates, bottom sheets, hardcoded strings, backup file names and the "frozen" astronomy all drifted. Prose does not enforce a rail. Each rail gets a cheap check (a Gradle task or a unit test that scans the repo) as ACTION_PLAN.md schedules them; pre-existing violations go into a baseline file that may only shrink (the ratchet), so a check can be switched on before the last violation is fixed. **Done in R0.2 (2026-11-12)** for two rails: protected-path hashes (`ProtectedPathsTest`, `config/protected.sha256`) and file size (`SizeRatchetTest`, `config/size-baseline.txt`); the other rails follow in ACTION_PLAN R4.

## 3. Architectural Rails (Non-Negotiable)
1.  **Main Activity is a Thin Orchestrator**: Root Activity owns only wiring and Intent parsing. All business logic lives in dedicated Manager classes.
2.  **Strict Localization (Zero Hardcoded Strings)**: Every user-facing string lives in `strings.xml` AND `values-fr/strings.xml`. French typography enforced (space before `:`, `;`, `!`, `?`, `»`). No hardcoded English in Kotlin/XML.
3.  **Portable Theme Engine**: The `:theme-engine` module exposes only a palette object of typed color tokens. No hardcoded hex in views/adapters. Contrast derives from background luminance, not theme identity.
4.  **Window & Inset Discipline**: Every Activity and full-screen Dialog uses edge-to-edge with 4-side `WindowInsets` padding (dialogs via `SystemBarContrastHelper`; small floating dialogs are exempt). The `verifyEdgeToEdge` Gradle gate enforces this. **NO bottom sheets anywhere.**
5.  **Performance Invariants**: Debounced inputs. Background sync via WorkManager (cache-first). Long computations on `Dispatchers.Default`. **No work on the main thread that can be deferred.**
6.  **Identity Stability**: Internal constants, preference keys, SharedPreferences file names and view IDs are **NEVER** renamed when display text changes. No drive-by refactors.
7.  **Migration Safety**: Removed features self-heal legacy preferences to safe defaults. Cached JSON is forward-compatible (unknown fields ignored).
8.  **RemoteViews (Widgets)**: Framework views only. PendingIntents use component-targeted intents with unique data URIs/request codes. Widgets invalidate synchronously from cache.
9.  **Documentation Collateral**: User-facing changes ship with matching updates to the website manual (usermanual.html), changelog (changelog.txt + changelog.html), and roadmap in the same sweep, unless explicitly deferred. **From gate R3.12 on** (in-app pages as bundled markdown, Adam 2026-11-12) the matching `assets/*.md` page is updated in the same sweep as its website HTML; a sync test fails the build when a heading or link in the HTML is missing from the markdown.
10. **Privacy statements are checked against the code (Adam, 2026-11-12).** The policy, the README and ARCHITECTURE.md say things about backups, analytics and alert consent. A gate that changes any of those facts updates the statements in the same sweep, and a gate that finds a statement false fixes either the code or the statement before it closes.

## 5. Known Traps & Common Agent Drifts
*Process drifts (seen with local and cloud agents):*
*   **Drift**: Replacing one hardcoded string with another instead of externalizing to `strings.xml`.
*   **Drift**: Renaming IDs or constants when only display text changes.
*   **Drift**: Proceeding to the next step without waiting for Adam's authorization.
*   **Drift**: Acting on stale docs. If ARCHITECTURE.md disagrees with the repo, the repo wins — flag it and fix the doc.
*   **Drift**: Putting "..." inside a raw-output block, retyping a diff by hand, or summarizing instead of pasting raw output (seen with every agent so far, Gemini included). Raw output is compared against the real command output.
*   **Drift**: Silently omitting hits it judges irrelevant instead of classifying them. Always reconcile table rows against raw output lines.
*   **Drift**: Claiming "zero references" without showing the grep and its raw output.
*   **Drift**: Drive-by edits (import removal, reformatting) outside the step's scope (Gemini did one).
*   **Drift**: Cleaning up byproducts unasked. AGENTS.md rule 8 forbids deleting anything a prompt does not name.
*   **Drift (Orchestrator)**: Writing "VERIFIED" or "frozen" as if it were a result. The freeze began as a guardrail against UI fixes that touch formulas and became a certificate nobody had earned. Protection and correctness are different claims (section 1, AGENTS.md rule 23).
*   **Drift (Orchestrator)**: Carrying notes forward. Open notes become a backlog that no gate owns; fix them in the gate (AGENTS.md rule 17).
*   **Drift (Orchestrator)**: Dictating constants or tables from memory (see section 1, "What the Orchestrator dictates").
*   **Drift (Coder)**: Changing a test's tolerance or expected value to make it pass (AGENTS.md rule 24).
*   **Drift (Coder)**: Fixing a "wrong looking" astronomy number by editing a formula or a UI conversion near it (AGENTS.md rule 23).
*Technical traps for this stack:*
*   **Trap (Coordinates)**: `Double` end-to-end. `Float` truncation causes 5-min solar errors. `LocationPreferences` still stores the fixed-default and last-used coordinates as Float (CODE_AUDIT L1).
*   **Trap (Empty Wipes)**: Providers returning `emptyList()` on error wipes the cache. Must use typed `AlertFetchResult.Failure`.
*   **Trap (Datamart Truth)**: Base URL is `/today/alerts/cap/`. SK maps to `CWWG`. Files are in `/HH/` folders. The three territories have no office-code mapping (CODE_AUDIT L5).
*   **Trap (Expiry Parsing)**: `expires` fields may have offsets (`+02:00`). Use `OffsetDateTime.parse`, not `Instant`.
*   **Trap (Memo keys)**: A cache or memo shared by several locations must carry the location in its key (the ECCC memo does not, CODE_AUDIT H1).
*   **Trap (Prefs names)**: SharedPreferences file names are used in code and in the backup XML; a rename in one place silently breaks the other (CODE_AUDIT H2, M2).
*   **Trap (Dismissals)**: Scoped to coordinates (`app_alert_dismissed_<lat>_<lon>_<id>`).
*   **Trap (Floating dialogs)**: Do not push small floating dialogs through the full-screen edge-to-edge helper (0.8.1 off-screen regression).
*   **Trap (Missing data)**: `?: 0.0` on forecast fields renders a missing value as a real zero (CODE_AUDIT M3).
*   **Trap (Astronomy time scales)**: Meeus series take TT (JDE); `AstroTime` converts UTC with ΔT. Mixing JD and JDE is the classic error. Sunrise and sunset use the apparent upper limb or a true altitude of -0.8333°, never both (ASTRONOMY_AUDIT H3).
*   **Trap (Date-dependent tests)**: A test that calls `LocalDate.now()` passes or fails by season.
*   **Trap (Statcounter)**: The in-app WebView runs JavaScript, so the Statcounter snippet in each `*.html` loads even from the cache (CODE_AUDIT H3).

## 6. Hand-off Protocol (Orchestrator continuity)
Orchestrator chats end (context limits, new day, model switch). HANDOFF.md is the single source of truth for "where are we". It lives in the claude.ai Project (so every new chat in the Project sees it) and in the repo for history. **HANDOFF.md is capped at 15 KB** (ported from vermilion, whose 138 KB file cost about 35k tokens on every resume). It holds the current state, the standing decisions in one line each, the current Coder profile, a pointer to ACTION_PLAN.md and the three newest session-log entries. History goes to `docs/archive/` in dated files; nothing is deleted.

**6.1 Session start (new Orchestrator instance)**
0. **First action once the Project docs are read: get the repo folder.** (These files are read from the claude.ai Project with the Projects tool, path `orchestration/<name>`; a fresh chat's working directory is empty, so never look for them on disk.) Call `get_device_info`; if `connectedFolders` lacks `/home/adam/AndroidStudioProjects/WeatherAPP`, call `device_request_folder_access` for that whole path (the grant covers the subtree). Ask once; if denied or unanswered, do not repeat, tell Adam and fall back to gated prompts or ask him to attach the folder. Use `device_bash` afterwards (mounted at `$HOME/mnt/WeatherAPP`, read-only git with `--no-optional-locks`).
1. Read AI_ONBOARDING.md, ARCHITECTURE.md, HANDOFF.md, ACTION_PLAN.md.
2. If the repo exists, compare HEAD with the commit recorded in HANDOFF.md. If they differ, read `git log` between them and note what changed.
3. Reply to Adam with a **State Readback** (max 8 lines): version/HEAD, active task and gate, what is awaited next, open decisions, and any drift found. End it with one extra line, not counted in the 8: **"Reminder: please check that this chat is set to Sonnet 5.5 with thinking level High."** (Adam's vermilion practice, adopted 2026-11-12 with his WeatherAPP setting: Sonnet 5.5, High; the Orchestrator cannot see or change that setting.) Do nothing else until Adam confirms or corrects it.
4. If the active task is mid-gate, resume from the "Next action" field — typically re-issuing or continuing from the recorded last prompt.

**6.2 Updating HANDOFF.md (Orchestrator)**
Update it (and write it back to the Project) at each of these moments, without being asked:
- a task completes its final gate;
- Adam makes a decision (including a DECISION item of ACTION_PLAN.md);
- Adam says "handoff", "wrap up", or that he's ending the session;
- the conversation is getting long (risk of context loss).
Rules: overwrite §1 Current State entirely; append one dated line per decision to §2; keep §3 as a pointer to ACTION_PLAN.md; prepend a §4 Session Log entry and keep only the 3 newest. Record the last issued prompt verbatim in §1 when a task is mid-gate — a new instance cannot recover it otherwise. If the file passes 15 KB, roll up first: move older decisions and log entries to a dated file in `docs/archive/`, leaving one line each.
**Sweeps (ported from vermilion):** documentation sweeps (end of task, end of milestone) are done by the Orchestrator, never by a Coder gate, except the website files named in rail 9, which a gate edits. ACTION_PLAN.md's status column is ticked in each gate's docs sweep. Every document claim about the code carries a tag in ARCHITECTURE.md: [V] verified by a command or test, [U] unverified, [F] known false today with its fix scheduled.

**Writing to Adam's computer (from vermilion, 2026-11-07):** a file built in the cloud workspace and sent with `device_commit_files` gets a staging name never used before in the session.
