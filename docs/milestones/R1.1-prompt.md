CONTEXT (BINDING):
- The bug. `EcccProvider.fetchAlertsForLocation` memoizes, per ECCC region and CAP file, the result of matching that file against ONE location: key `"eccc_memo_${ecccCode}_${filename}"`, value `EcccMemoEntry(matched, timestamp, alert)` where `alert` is a `UnifiedAlert` built for that location (its `locationLat` and `locationLon` are that location's). Two tabs in one region (Ottawa and Toronto both resolve to `CWTO`) share the key, so the second tab receives the first tab's verdict: a file that did not match the first location is skipped for the second (a missed alert), and a file that did match returns the first location's `UnifiedAlert` to the second (wrong coordinates; dismissals and notification ids are scoped to them).
- The fix (decided; this is the plan required by rule 10). The location goes into the key. New key: `"eccc_memo_${ecccCode}_${location.latitude}_${location.longitude}_${filename}"`, using the Kotlin `Double` string form, for example `eccc_memo_CWTO_43.6532_-79.3832_<file>`. Coordinates are used because dismissals are coordinate-scoped and a tab's `id` can be 0. The prefix `eccc_memo_` stays, so `DefaultEcccMemoStore.loadFromPrefs` and the purge still see every entry. `EcccMemoEntry`, `EcccMemoStore`, `UnifiedAlert`, `AlertMatcher`, `CapXmlParser` and the prefs file name `eccc_memo_prefs` do NOT change. Entries in the old key format are never read again and leave the store with the existing 48-hour purge. Cost: two tabs in one region fetch each CAP file once each on their first sync; later syncs use the memo.
- Size. `app/src/main/java/com/weatherapp/libre/alerts/providers/EcccProvider.kt` is 510 lines and is listed in `config/size-baseline.txt`; it may not grow (`SizeRatchetTest`). The fix replaces one line with one line.
