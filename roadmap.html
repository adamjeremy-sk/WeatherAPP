Executive Summary

WeatherAPP Libre possesses a strong, highly differentiated product concept centered on privacy, transparency, and specialized astronomical and weather features. The project has undergone focused remediation of data attribution, astronomical accuracy, and testing frameworks, with alert integrity remaining the primary outstanding critical risk.

A private, ad-free weather and natural-light planner for photographers, outdoor users, and astronomy enthusiasts, featuring selectable forecast models and zero GPS tracking.

1. Phase 1: Trust, Safety & Compliance

1.1 Alert Integrity Remediation

Critical Requirement: Forecast-model conditions must never be labeled as official ECCC or CAP-CP alerts.
  • Implement official alert sourcing via a verified CAP-CP feed, preserving original identifier, issuer, timestamp, severity, and expiry.
  • Rebrand model-derived severe weather conditions as "WeatherAPP Forecast Advisory" or "Potential Severe Weather."
  • Ensure no safety-critical alert functionality is gated behind a paywall.

1.2 Astronomical Data Validation

  • Rebuild the astronomical dataset from documented, authoritative sources.
  • Implement automated validation to reject impossible phase intervals (e.g., first quarter occurring one day after a new moon).
  • Store event times in UTC and include visibility regions where applicable.
  • Remove or replace placeholder lunar azimuth calculations with a defensible lunar-position algorithm.

1.3 Licensing and Attribution Compliance

  • Update UI attribution to clearly state: "Forecast model: Environment Canada GEM | Weather data provided by: Open-Meteo."
  • Formalize the commercial-use arrangement with Open-Meteo to ensure compliance with their pricing and terms of service.

2. Phase 2: Core User Value & Accuracy

2.1 Calculation and Display Refinements

  • Correct solar-noon elevation to account for the absolute difference between latitude and solar declination.
  • Implement explicit "NeverOccurs" or "AlwaysAboveThreshold" states for polar night and midnight sun, avoiding artificial midnight boundary clamping.
  • Rename calculate13ChronologicalPhases() to accurately reflect its 15-entry output.
  • Relabel "Ceiling" to "Estimated cloud base" with a clear disclaimer, or remove the metric entirely.

2.2 High-Value Feature Additions

  • Integrate hourly forecasts and precipitation probability (contingent on API licensing).
  • Implement visible "last refreshed" and "cached data" indicators.
  • Develop a home-screen widget for immediate at-a-glance utility.
  • Introduce a forecast-model comparison screen displaying model update timestamps.
  • Implement French localization to serve the Canadian market effectively.
  • Ensure all themes pass accessible contrast ratio testing and include a reduced-motion option.

3. Phase 3: Technical Architecture & Stability

3.1 Architectural Decoupling

  • Decompose the monolithic MainActivity into focused components: MainViewModel, WeatherUiState, AlertCoordinator, ThemeCoordinator, and LocationTabsController.
  • Expose immutable UI state exclusively through StateFlow.
  • Migrate persistent cache storage from SharedPreferences to Room database or structured file storage.

3.2 Networking and Data Integrity

  • Construct all network URLs using HttpUrl.Builder to prevent injection and formatting errors.
  • Inject OkHttpClient and Gson dependencies for testability.
  • Implement request deduplication and memory-cache eviction policies.
  • Map external DTOs into immutable domain models; do not mutate API response objects directly.
  • Retain Double precision for coordinates; utilize location IDs or rounded coordinates for cache keys.

3.3 Testing Matrix Implementation

Establish automated test coverage for the following edge cases:

  • Daylight-saving transitions and Saskatchewan's non-DST behavior.
  • Locations east and west of the International Date Line.
  • Southern Hemisphere solar noon and Arctic summer/winter extremes.
  • Malformed XML records and impossible lunar-phase sequences.
  • Cache expiry, offline fallback, and concurrent duplicate requests.

4. Phase 4: Release Preparation & Compliance

4.1 Privacy and Store Compliance

  • Publish a comprehensive privacy policy detailing data transmission (latitude/longitude to Open-Meteo, IP metadata, geocoding terms).
  • Ensure the Google Play Data Safety declaration accurately reflects the absence of advertising, analytics, and GPS tracking SDKs.
  • Implement a one-tap "Delete local app data" control within the application settings.
  • Externalize all hardcoded interface strings into Android string resources.

5. Production Release Gates

The application must not proceed to public release until the following non-negotiable criteria are met and verified by QA:

Mandatory Release Criteria:
  1. Alert labeling is strictly truthful, safe, and legally compliant (no synthetic ECCC alerts).
  2. Open-Meteo attribution is visibly implemented, and commercial-use licensing is formally resolved.
  3. Core architecture refactoring (ViewModel, StateFlow) is complete and covered by automated tests.

Note: Astronomical data validation (Section 1.2) and core privacy compliance (Section 4.1) have been satisfied and are no longer blocking release gates.
