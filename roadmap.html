Executive Summary

WeatherAPP Libre possesses a highly differentiated product concept centered on privacy, transparency, and specialized astronomical features. The project has executed a massive architectural refactoring, replacing a monolithic codebase with a modular Manager-driven architecture, rebuilding its solar and lunar engines using rigorous topocentric mathematics, and successfully completing the official ECCC CAP-CP alert integration.

A private, ad-free weather and natural-light planner for photographers, outdoor users, and astronomy enthusiasts, featuring selectable forecast models and zero GPS tracking.

1. Phase 1: Trust, Safety & Compliance

1.1 Alert Integrity Remediation

  • Remove all synthetic model-derived severe weather conditions masquerading as official alerts.
  • Implement official alert sourcing via a verified CAP-CP feed, preserving original identifier, issuer, timestamp, severity, and expiry.
  • Execute the CAP-CP agent prompt to finalize background WorkManager polling, XML parsing, and polygon/circle matching.

1.2 Astronomical Data Validation

  • Rebuild the astronomical dataset from documented, authoritative sources (Jean Meeus).
  • Implement automated validation to reject impossible phase intervals.
  • Store event times in UTC and include visibility regions where applicable.
  • Replace placeholder lunar azimuth calculations with iterative topocentric root-finding.

1.3 Licensing and Attribution Compliance

  • Update UI attribution to dynamically reflect the active forecast model (e.g., "Data: DWD via Open-Meteo").
  • Publish comprehensive Licenses & Sources page detailing all data providers and open-source libraries.
  • Formalize the commercial-use arrangement with Open-Meteo to ensure compliance with their pricing and terms of service.

2. Phase 2: Core User Value & Accuracy

2.1 Calculation and Display Refinements

  • Correct solar-noon elevation to account for the absolute difference between latitude and solar declination.
  • Implement explicit "NeverOccurs" or "AlwaysAboveThreshold" states for polar night and midnight sun, avoiding artificial midnight boundary clamping.
  • Refactor solar display to focus on azimuth angles rather than duplicating sunrise/sunset times.
  • Remove the unreliable "Ceiling" metric entirely from the UI and data models.

2.2 High-Value Feature Additions

  • Ensure all themes pass accessible contrast ratio testing and include a reduced-motion option.
  • Integrate a 36-hour Hourly Forecast with expandable stat panels and theme-reactive surfaces.
  • Replace all weather condition emojis with a custom, theme-reactive 28-state vector icon set.
  • Restructure inline sub-tabs into Current, Hourly, and Natural Light categories.
  • Implement 7-Day Forecast placement control (inline vs. dropdown menu) and a comprehensive Menu Organization screen (drag-to-reorder, visibility toggles, default launch page, separators).
  • Create and integrate a comprehensive in-app User Manual accessible from the navigation drawer and Info screen.
  • Implement visible "last refreshed" and "cached data" indicators.
  • Develop a home-screen widget for immediate at-a-glance utility.
  • Introduce a forecast-model comparison screen displaying model update timestamps.
  • Implement French localization to serve the Canadian market effectively.

3. Phase 3: Technical Architecture & Stability

3.1 Architectural Decoupling

  • Decompose the monolithic MainActivity into focused components (ThemeManager, WeatherDisplayManager, AstronomyDisplayManager, LocationTabsManager, etc.).
  • Decompose activity_main.xml into composed section layouts to eliminate deep LinearLayout nesting.
  • Convert repeated hand-written metric cells into a RecyclerView grid backed by an adapter.

3.2 Testing Matrix Implementation

Establish automated test coverage for the following edge cases:

  • Daylight-saving transitions and Saskatchewan's non-DST behavior.
  • Locations east and west of the International Date Line.
  • Southern Hemisphere solar noon and Arctic summer/winter extremes.
  • Malformed XML records and impossible lunar-phase sequences.
  • Topocentric lunar parallax, horizon dip, and atmospheric refraction edge cases.
  • Curate and harden unit test suite, removing diagnostic scaffolding and enforcing deterministic invariants (78 passing tests).

4. Phase 4: Release Preparation & Compliance

4.1 Privacy and Store Compliance

  • Publish a comprehensive privacy policy detailing data transmission (latitude/longitude to Open-Meteo, IP metadata, geocoding terms).
  • Ensure the Google Play Data Safety declaration accurately reflects the absence of advertising, analytics, and GPS tracking SDKs.
  • Standardize website navigation, typography, and layout across Home, About, Licenses, and Roadmap pages.
  • Implement a one-tap "Delete local app data" control within the application settings.
  • Enable R8 code shrinking, obfuscation, and resource optimization for release builds to meet Play Console DEX optimization requirements.
  • Externalize all hardcoded UI strings to strings.xml to establish a comprehensive localization infrastructure.

5. Phase 5: Advanced Features & Expansion

With the core architecture stabilized, development shifts to high-value utility features and intelligent data routing.

5.1 Diagnostic Logging Dashboard

  • Build an in-app Logs screen accessible via the navigation drawer.
  • Implement an internal event logger for lifecycle, cache, and resolution events.
  • Add clipboard export and secure email-to-support functionality.

5.2 Lunar Utility Pages

  • True Dark Sky Window: Calculate periods of astronomical darkness overlapping with low lunar interference.
  • Night Visibility Forecast: Estimate ambient light potential based on moon phase, altitude, twilight, and cloud cover.
  • Solunar Activity Forecast: Display traditional major/minor solunar periods based on lunar transit and nadir.

6. Production Release Gates

The application must not proceed to public release until the following non-negotiable criteria are met and verified by QA:

Completed Release Criteria:
  • Official ECCC CAP-CP alert pipeline is fully implemented, tested end-to-end, and strictly truthful (zero synthetic alerts).
  • Comprehensive automated test suite passes consistently across all architectural modules.
  • All hardcoded UI strings are externalized to strings.xml to support future localization.
  • DEX code optimization and R8 obfuscation enabled for release builds.
Pending Release Criteria:
  • Open-Meteo commercial-use licensing is formally resolved and documented.

Note: Core architecture refactoring, astronomical data validation, layout decomposition, accessibility compliance, baseline privacy compliance, and official ECCC CAP-CP alert integrity have been satisfied and are no longer blocking release gates.
